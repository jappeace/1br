# Why 1br is slow on THC, and what would make it faster

With THC's defaults a billion rows would take about 39 minutes. Two
compiler settings bring that to 2.6 to 2.8 minutes, measured: Graal's graph-size
budget raised from 100 000 to 400 000 and on-stack replacement (OSR) turned
off. A 17-line runtime patch then brings it to 1.8 to 1.9 minutes. Native GHC needs
1.3 seconds. This file records what was measured, how the time was
attributed, and which changes would help, with an estimate of the work.

Everything was measured on 3 October 2026 on the scoreboard's laptop (Ryzen
AI 7 350, 8 cores, 16 threads) with THC at `0ae57cbf` unless a row says
otherwise, on an otherwise idle host. Every run reported here printed the
native program's report byte for byte.

## Measurements

| configuration | 10M rows | 100M rows | 1B rows |
|---------------|----------|-----------|---------|
| native, GHC 9.12.2 -O2 | 0.040 s | 0.151 s | 1.32 s |
| THC `6610dc01` (the previous pin), defaults | 38.2 s | 235 s | ~38 min extrapolated |
| THC `0ae57cbf`, defaults | 37.7 s | 243 s | ~39 min extrapolated |
| graph budget 400 000 | 20.1 s | 181 s | |
| graph budget 400 000, OSR off | 21.0 s | 39.4 s | 154.5 s, 166.3 s, 161.2 s |
| the same plus the word-read patch (below) | | 36.9 s | 108.8 s, 115.5 s |
| AST backend instead of bytecode, defaults | 49.2 s | | |

10M rows are the mean of three runs for the default and tuned rows; the
graph-budget-only and AST rows are single runs with instrumentation
attached. The 100M rows with OSR off are the mean of three runs, the others
single runs. A 20-row file takes 10.8 s on either THC revision; that
start-up is in every THC number. The 1B extrapolation is that start-up
plus ten times the rest of the 100M run.

The update from `6610dc01` to `0ae57cbf` (177 commits, the two pins a
day apart) left 1br's default-configuration numbers where they were; the
tuned configurations below were only run on `0ae57cbf`. The GHC submodule, the Graal version and
the hardcoded graph budget did not change.

## Where the time goes with THC's defaults

The lambda that walks a chunk (`pairLineLoop` with `stepLine`,
`scanValue` and `finishLine` inlined) is too big for the budget: every
compile attempt bails out at a graph size of 100 001 to 100 008. THC's
graph recovery then builds a replacement root that splits the lambda's
case regions into separate call targets, and redirects the old root to
it ([`BytecodeRoot.java`](https://github.com/ekmett/thc/blob/0ae57cbfe6a4fde15efbc17ffb1852694307e617/src/main/java/thc/runtime/BytecodeRoot.java#L75-L90)):
the old root's prolog throws the preallocated `EnterRecovered` exception
on every entry, and `interceptControlFlowException` forwards the call to
the replacement. Truffle's generated Bytecode DSL handler calls
`transferToInterpreter()` before it hands a control-flow exception to that
method. Most loop iterations re-enter the old root, so compiled code
deoptimizes on most iterations, and because the transfer does not
invalidate, it never stops.

| observation (10M rows, defaults) | value |
|----------------------------------|-------|
| deoptimizations (JFR `jdk.Deoptimization`), all `transfer_to_interpreter` | 4 218 412 |
| of the first 114 458 transfers traced with `engine.TraceTransferToInterpreter` on 1M rows, at `handleControlFlowException` | 100% |
| loop iterations (THC's `tailBounces`) / of which looped in place (`selfTailReentries`) | 5 541 616 / 735 402 |
| deoptimizations per iteration that crossed roots | 0.88 |
| JFR CPU-time samples whose top frame is the deoptimization's frame state | 54.6% of the kept samples, 22% were lost, so 42% to 65% of all |
| voluntary context switches | 5.1M (0.89M once the loop compiles) |
| allocated | 15.0 GB, about 1.5 KB per row |

JFR files these deoptimizations under `ApplyTypedInput.apply`, line 2402,
the frame state Graal attached to them: the `finally` block's
`clearSource` call, eight lines below a `catch (AstCapture)` that
transfers to the interpreter. That catch was a false lead. JFR's exception events
recorded no `AstCapture` construction at all, and a one-line patch
removing its transfer only moved the reported site into `clearSource`'s
callee `FrameWithoutBoxing.clear`, at its `return`. Truffle's own tracer
records the call site of each transfer and gives the real one.

## Why a bigger budget alone stops working at 100M

With a budget of 400 000 the whole lambda compiles: 8.4 s of compile
time, 106 215 IR nodes, 544 KB of machine code. 10M rows drop to 20 s
with 487 deoptimizations. At 100M the gain shrinks to 181 s, because the
same lambda's OSR variant is compiled as well and its installation fails
after 9 to 11 s of compiling with "Code installation failed: code is too
large".
[`GraphRecovery.failed`](https://github.com/ekmett/thc/blob/0ae57cbfe6a4fde15efbc17ffb1852694307e617/src/main/java/thc/runtime/GraphRecovery.java#L82)
counts that message as a terminal graph failure, `GraphRecovery.source`
maps the OSR root to the lambda, and 69 ms later THC invalidates the
working compilation of the lambda ("validRootAssumption fresh bytecode
entry after terminal graph-size failure"). From then on the run is in the
split mode above: THC's counters show 33.05M of the 55.34M loop
iterations crossing roots.

With `-Dpolyglot.engine.OSR=false` the whole-lambda compilation stays:
100M rows take 39.4 s, all 55.3M iterations loop in place, and the run
deoptimizes about 500 times.

## What is left once the loop is compiled

At 100M rows the tuned run is 10.8 s of start-up, about 13 s of steady
state (from the 1B runs below), and about 15 s that remain, which is
warm-up: workers interpret until the 8.4 s compile of the lambda lands. At a billion rows the steady state dominates: 13.4 s per
100M rows, 2.0 µs of CPU per row against native's 16 ns.

Memory reads through `Addr#` cost the most there. Each `peekWord64` is a
`plusAddr#`, which allocates a `ManagedAddress` and takes one borrow to
check the allocation is live, then a `readWord64OffAddr#`, which takes a
borrow, checks the range under another borrow, and assembles the word
from eight single-byte reads that each take two more borrows behind a
`@TruffleBoundary`. A borrow is a read lock on a fair
`ReentrantReadWriteLock` plus a `Borrow` object, so one 8-byte load costs
19 lock acquisitions, and the hot loop does three loads per row. In JFR's
samples at 100M those locks and address checks are 37% of CPU. The
prototype in [nix/patches/native-word-read.patch](nix/patches/native-word-read.patch)
serves the word with one borrow and one 8-byte load. Run cold, with three
idle minutes before each, a billion rows drop from 161 s to 109 s and CPU
time by 38%; an earlier back-to-back pair gave 166 s and 115 s. At 100M the same patch is within
noise (36.9 ± 2.6 s against 39.4 ± 1.0 s), because start-up and warm-up
dominate there.

The tuned 100M run allocates 54 GB in total, about 0.54 KB per row
including start-up and warm-up: boxed `Long` values written to Bytecode
DSL frame slots 44%, `ManagedAddress` objects from `plusAddr#` 34%,
`Borrow` objects 12%.

Table set-up is a smaller cost. `setPrimArray` calls primitive's C
`hsprimitive_memset_Word`, which runs in Sulong and calls back for every
pointer it touches into `NativeAddresses.project`. That method is
synchronized on the context and rescans the whole address registry
(`reap`, two `removeIf` passes) on each call, with 16 workers doing it at
once. It shows up as about 1M voluntary context switches per run and 6%
to 21% of samples. Replacing `setPrimArray` with a Haskell write loop (an
experiment, not committed) removes most of those context switches but
changes no wall time within noise (37.3 ± 3.0 s at 100M, 162.5 s at 1B),
because the set-up overlaps the lambda's compile.

Hash-table reads (`readIntArray#` on a pinned array) synchronize on the
array's owner per access, which is 1% to 4% of samples.

## Improvement candidates

Difficulty is an estimate of the work in THC: trivial means a flag,
small a contained change in one class, moderate a change across THC's
lowering or runtime model, hard a change to one of THC's design
decisions.

| # | change | where | effect | difficulty |
|---|--------|-------|--------|------------|
| 1 | Make the graph budget configurable and run 1br with a raised budget (400 000 is the only value measured on this pin) and OSR off | THC launcher (`Main.java` hardcodes 100 000), JVM flags | measured: 1B from ~39 min to 2.6 min, 100M from 243 s to 39 s | trivial for 1br ([nix/thc-runtime-tunable.nix](nix/thc-runtime-tunable.nix) is four substitutions); choosing a new default is THC's call, since bigger graphs mean multi-second compiles |
| 2 | Keep a failed OSR install from invalidating the root's working compilation | `GraphRecovery` | inferred: OSR could stay on and 100M would match the OSR-off 39 s instead of 181 s | small, one condition; the code maps OSR roots on purpose, so it needs the maintainer's reason |
| 3 | Redirect callers to the recovered root instead of throwing `EnterRecovered` on every entry | `BytecodeRoot` recovery | removes 4.2M deoptimizations per 10M rows, 42% to 65% of CPU samples with defaults; split mode still crosses roots on 87% of iterations, so the result stays well behind #1 | moderate: rewrite the dispatch caches that hold the old target, or ask Truffle for a handler that does not deoptimize |
| 4 | Read native words with one borrow and one load | `ManagedAddressRead`, `ManagedAddress` | measured with the prototype: 1B from 161 s to 109 s cold, CPU down 38% | small to moderate: the prototype is 17 lines; upstream has to keep the borrow guarantees for every address kind |
| 5 | `plusAddr#` without an allocation and a borrow | `ManagedAddress.plus`, lowering | 34% of the allocation; not measured | moderate: offsets carried in typed locals instead of a new object |
| 6 | Unboxed `Long` locals in Bytecode DSL frames | bytecode lowering | 44% of the allocation; not measured | moderate to hard |
| 7 | `NativeAddresses.project` without the context lock and full rescan, or a Java intrinsic for primitive's memset family | `NativeAddresses` | measured via the 1br-side experiment: context switches from ~1M to 0.13M to 0.26M, no wall-time change | small for an incremental reap, moderate for intrinsics |
| 8 | Shorter warm-up: smaller graphs for big lambdas, or compiled code cached between runs | THC compiler, native code cache | about 15 s of a 39 s 100M run | hard |
| 9 | Shorter start-up | THC launcher, Native Image | 10.8 s per run | hard; THC's native code cache and Native Image support are experimental |
| 10 | Rewrite 1br's hot loop over `MutableByteArray` instead of `Ptr` | 1br | not measured | moderate, and it defeats running the unmodified source |

The AST backend is no way out: it is slower (49.2 s at 10M). Nor would
more compiler threads shorten warm-up, since Graal compiles one call
target on one thread and the 8.4 s compile is a single call target.

## Instruments

All runs used the launcher from [acquire.sh](acquire.sh) with
`ONEBR_THC_RUNTIME` pointing at a build of
[nix/thc-runtime-tunable.nix](nix/thc-runtime-tunable.nix) (or the
native-word variant), plus these JVM options in `JAVA_OPTS`:

| question | options |
|----------|---------|
| tuned configuration | `-Dthc.tune.MaximumGraalGraphSize=400000 -Dpolyglot.engine.OSR=false` |
| what compiles, fails and invalidates | `-Dthc.traceCompilation=true -Dpolyglot.engine.CompilationStatistics=true` |
| THC's own counters (bounces, compiled entries) | `-Dthc.diagnostics=true` |
| where compiled code deoptimizes | `-Dpolyglot.engine.TraceTransferToInterpreter=true` (use 1M rows, it prints a stack per transfer) |
| CPU, allocation and deoptimization counts | `-XX:StartFlightRecording=filename=run.jfr,settings=thc-profile.jfc,maxsize=0`, where `thc-profile.jfc` is JDK 25's `profile.jfc` with `jdk.CPUTimeSample` enabled at 10 ms, `jdk.Deoptimization` without stack traces and `jdk.graal.compiler.truffle.Deoptimization` disabled |
| GC and allocation volume | `-Xlog:gc:file=gc.log` |

Two JFR pitfalls cost a round of measurements each. Without `maxsize=0`
JFR caps a recording at 250 MB and drops its oldest chunks, which the
deoptimization events fill within seconds. Truffle registers its event
types after the JVM starts, so a command-line setting for
`jdk.graal.compiler.truffle.Deoptimization` is rejected; a `.jfc` file
applies it.
